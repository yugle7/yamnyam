# Задача: поисковый индекс по каталогу продуктов

## Роль и цель

Ты — senior Python-инженер. Реализуй поиск по каталогу [foods.jsonl](foods.jsonl) (22 283 JSONL-записи). По свободному запросу пользователя нужно вернуть наиболее релевантный продукт с учетом:

- названия (`name`, `alternative_names`);
- бренда (`brand`);
- способа приготовления (`cook`).

Результат: лучшее совпадение

## Входные данные

Запись содержит:

```json
{
  "name": "курица, грудка",
  "brand": "петелинка",
  "cook": "жареное",
  "alternative_names": ["куриная грудинка"]
}
```

`brand` и `cook` могут отсутствовать или быть неканоническими. `nutrients` и другие справочные поля в поиске не участвуют. Исходный файл не изменять.

## Алгоритм

### 1. Нормализация

Единая для индекса и запроса:

- считай что запрос и все названия уже нормализованы и приведены к нижнему регистру;
- лемматизация русских слов (`pymorphy3` или аналог);
- бренды не лемматизировать агрессивно;
- транслитерация латиница в кириллицу;
- запрос не содержит количество и вес;
- сохранять `без`, `с`, `на` и отрицания.

### 2. Подзапросы блюда

Для каждой записи сгенерируй побольше уникальных подзапросов:

- `name_full` — нормализованное полное название;
- `name_core` — название без бренда и cook;
- `alternative_name` — каждый `alternative_names`;
- комбинации: `brand+name`, `name+cook_family`, `brand+name+cook_family`;
- транслитерации;

`cook_family` — обобщенный способ: `жарка`, `варка`, `запекание`, `копчение`, `соление` и т.п.

### 3. Индекс и фильтрация

Построй индекс `подзапрос → список id`. Для каждого подзапроса сохрани `df` и `idf`.

Удали слишком общие подзапросы:

- по умолчанию `df > 100`;
- пороги должны быть настраиваемыми;
- у каждого блюда оставь хотя бы один fallback-подзапрос;
- если запрос целиком состоит из общих слов, разреши fallback-ранжирование по токенам/BM25.

### 4. Парсинг запроса

Верни структуру:

```json
{
  "name": "куриная грудка",
  "brand": "петелинка",
  "cooks": ["жарка"]
}
```

Правила:

- искать бренды по словарю, самое длинное совпадение, с учетом транслитерации;
- искать cook по словарю и словоформам: `жареный/жареная/жареные → жарка`, `вареный → варка`, `запеченный → запекание`;
- все остальное — `name`;
- не выдумывать бренд по общему слову;
- вкусовые прилагательные не считать cook: `соленая карамель` — вкус, а не `соление`.

### 5. Подзапросы запроса

Сгенерируй ограниченный набор:

- полный нормализованный запрос;
- `name`, каждый бренд, каждый cook;
- `brand+name`, `name+cook`, `brand+name+cook`;
- токены/биграммы названия;
- транслитерации;

Веса: точное полное совпадение > `brand+name+cook` > `name` > `alternative_name` > `бренд+cook`.

### 6. Кандидаты и ранжирование

1. Найди кандидатов по postings-list каждого подзапроса.
2. Объедини и дедуплицируй.
3. Посчитай score:

```text
idf(q) = log(1 + N / df(q))

base = Σ [ w_query(q) * field_weight * idf(q) * matched(q) ]

score = base
      + 0.5 * max(exact_alternative_name_bonus, exact_name_bonus)
      + 0.3 * phrase_bonus
      + 0.5 * brand_bonus       # только если бренд есть в запросе
      + 0.3 * cook_bonus        # только если cook есть в запросе
      - 0.6 * conflict_penalty  # бренд/cook противоречит запросу
```

- `field_weight`: name > brand > cook.
- Если в запросе нет бренда/cook — соответствующий бонус `0`, без штрафа.
- Жесткую фильтрацию по бренду/cook не применять, если кандидатов остается слишком мало.
- Tie-break — детерминированный (например, меньший `id`).

### 7. Выдача

Верни:

- `result`;
- `confidence`;

JSON-формат:

```json
{
  "query": "жареная куриная грудка петелинка",
  "confidence": 0.83,
  "result": {
      "id": 12345,
      "name": "грудка куриная жареная",
      "brand": "петелинка",
      "cook": "жарка на сковороде",
      "score": 12.4,
      "matched_subqueries": ["brand+name+cook"],
      "explanation": "совпали бренд, название и cook"
    }
}
```

## CLI

```bash
python -m food_search build  --foods foods.jsonl --index index/
python -m food_search search --index index/ --query "жареная курица" --json
python -m food_search eval   --index index/ --queries eval/queries.jsonl
```

## Технические требования

- Python 3.12+.
- Без внешних поисковых серверов.
- Индекс детерминирован, повторная сборка дает тот же результат.
- Память ≤ 500 МБ.
- Поиск p95 < 20 мс.
- Никаких сетевых запросов при поиске.
- Type hints, docstrings, тесты.

## Deliverables

1. Код с CLI `build`, `search`, `eval`.
2. Индекс в `index/`.
3. `README.md`: архитектура, пороги, веса, метрики, ограничения.
4. `tests/`.
5. `eval/queries.jsonl` — не менее 100 запросов с правильными `id`.
6. Отчет: `Recall`, latency.

## Критерии приемки

- Точные названия/алиасы: `Recall ≥ 0.95`.
- Бренд + cook: `Recall ≥ 0.80`.
- Тесты проходят.
- Запросы без бренда/cook не деградируют.
- `build` и `search` воспроизводимы.

## Крайние случаи

Пустой запрос; только бренд; только cook; общие слова; неизвестный бренд; опечатки; транслитерация; скобки/запятые/дефисы; числа и единицы; отрицания; одинаковые названия у разных брендов/cook; отсутствующие поля; длинный запрос; все подзапросы отфильтрованы.

## Вне рамок

Веб-интерфейс, изменение БД, обучение нейросетей, Elasticsearch/OpenSearch, внешние API.
